## 1. 제품 목표

**처음 온 사람이 가입하거나 냉장고를 등록하기 전에도 남은 재료로 메뉴를 고르고, 필요한 재료와 조리법까지 확인할 수 있게 한다.** 재료를 저장한 사용자는 같은 흐름에서 보유 재료와 먼저 활용할 재료에 맞춘 도움을 받는다.

이 목표를 다음 세 가지 결과로 확인한다.

1. 공개 페이지가 운영 도메인에서 실제 본문과 함께 열린다.
2. 메뉴 선택 이유·부족 재료·조리법이 서로 일치한다.
3. 기존 레시피 원문에 더해, 냉장고 재료를 어떻게 활용할지 판단하는 데 도움이 된다.

AdSense 승인은 외부 심사 결과다. 이 계획의 완료 기준은 서비스 품질과 검증 가능한 공개 상태이며 승인을 보장하지 않는다.

## 3. 화면 구조

기존 경로를 활용한다. 공개 콘텐츠를 보다가 원하는 시점에 재료 관리로 넘어가도록 한다.

| 화면 | 주요 역할 | 보여줄 내용과 다음 행동 |
| --- | --- | --- |
| `/` 홈 | 첫 방문 가치 전달, 재방문자의 할 일 안내 | 첫 방문: 재료별 메뉴·대표 사례·공개 레시피. 재료 저장 후: 먼저 볼 재료·맞춤 메뉴를 우선 배치하고 공개 탐색도 유지 |
| `/recipes` 메뉴 | 공개 탐색과 내 재료 추천의 출발점 | 데이터 없음: 재료별 탐색. 데이터 있음: 보유·부족·먼저 활용할 재료를 근거로 후보 제시 |
| `/recipes/ingredients/:slug` 재료 허브 | 같은 재료로 가능한 메뉴 비교 | 추가 핵심 재료, 필요한 도구, 원문 기준 사용량, 선택 이유와 상세 링크 |
| `/recipes/:slug` 레시피 상세 | 준비와 조리를 끝까지 안내 | 원문의 분량·단계·사진·출처 + 검토한 활용 설명 + 보유 여부와 부족 재료 확인 |
| `/guides/:slug` 활용 가이드 | 실제 선택 과정을 설명 | 예시 냉장고 → 메뉴 비교 → 선택 근거 → 필요한 구매 항목 → 해당 상세 페이지 |
| `/ingredients`, `/import`, 계정 화면 | 개인 재료 관리 | 기존 로컬 저장·OCR 검토·계정 흐름을 유지하며 공개 콘텐츠로 돌아오는 링크 제공 |

기본 동선: **홈에서 재료 선택 → 후보 비교 → 내부 레시피 상세 → 필요한 경우 냉장고에 기록**.

예시 냉장고는 예시임을 표시하고 사용자 보유 데이터와 섞지 않는다. 실제 저장은 사용자가 명시적으로 선택했을 때만 한다. 개인 냉장고 내용은 공개 HTML·사이트맵·공개 구조화 데이터에 포함하지 않는다.

## 4. 단계별 작업과 완료 기준

### P0. 배포 일치성 복구

작업:
- 실제 운영 프로젝트·배포 ID·연결 브랜치/커밋·도메인 대상을 확인한다.
- 기존 미커밋 수정 파일을 보존하고, 배포할 소스를 확정한다.
- `npm run build`, `dist`, SEO postbuild가 운영 배포에 반영되는지 확인한다.
- 공개 URL 목록과 빌드 산출물, 운영 응답을 비교하는 검증 절차를 둔다.

완료 기준:
- 현재 공개 대상으로 구성한 113개 URL이 운영에서 200이며 제목과 해당 본문을 반환한다. 홈 HTML로 대체된 200은 통과시키지 않는다.
- 사이트맵·canonical·내부 링크가 일치하고, 없는 경로는 404다.
- 실제 배포 커밋과 검증 결과를 기록해 다음 배포에서도 같은 검사를 수행할 수 있다.

의존성: 실제 운영 프로젝트를 조회할 수 있는 계정/프로젝트 정보. 현재 연결된 Vercel 계정에서는 대상 배포를 찾지 못했다. 이 확인을 기다리는 동안 P1과 콘텐츠 초안 작업은 진행할 수 있다.

113은 현재 소스와 운영을 맞추는 기준이며 승인 최소 페이지 수가 아니다. 공개 범위를 변경한다면 경로 목록·사이트맵·검증기·이 계획을 함께 갱신한다.

### P1. 추천 신뢰성 수정

작업:
- 입력 데이터가 없는 상태, 팬트리만 있는 상태, 일반 재료가 있는 상태를 구분한다.
- 입력 전에는 ‘메뉴 둘러보기’로 안내하고 맞춤 점수·보유 매칭 주장을 표시하지 않는다.
- 실제 보유 재료와 필수 재료 그룹을 모두 확인한 뒤 ‘바로 가능’, ‘하나만 더’, ‘양념만 보완’ 설명을 만든다.
- 분모가 0인 매칭률·일치 개수 표현을 정리한다.
- 메뉴 선택 클릭은 실제 상세 이동이나 명확한 행동을 제공하도록 정리한다.

완료 기준:
- 재료 0개에 ‘핵심 재료가 대부분 맞음’이 나오지 않는다.
- 팬트리만 보유, 필수 그룹 누락, 핵심 재료 1개 부족, 핵심 재료 충족의 설명이 실제 결과와 일치한다.
- 위 시나리오를 회귀 테스트로 검증하고 기존 pantry-aware 점수와 추천 그룹을 유지한다.

주요 대상: `src/utils/recommendations.js`, `src/components/RecipeCard.jsx`, `src/pages/RecipesPage.jsx`.

### P2. 공개 탐색과 내부 상세 연결

작업:
- 홈 첫 화면에 공개 메뉴 진입점과 구체적인 활용 사례를 배치한다.
- `/recipes`에서 입력 전에도 공개 카탈로그를 탐색하도록 하고 주요 콘텐츠·링크를 프리렌더한다.
- 추천 64개와 공개 상세 100개는 확인한 항목부터 안정적인 ID로 연결한다. 제목이 비슷하다는 이유만으로 다른 조리법을 연결하지 않는다.
- 연결되지 않은 메뉴는 외부 검색임을 분명히 표시하고, 내부 조리법이 있는 것처럼 동작하지 않게 한다.
- 상세 페이지에 보유 여부와 부족 재료를 연결한다. 현재 수량 입력이 자유 형식이므로 초기에는 ‘있는 재료/없는 재료’를 기준으로 하고 보유량이 충분하다고 단정하지 않는다.

완료 기준:
- 비로그인·저장 재료 0개 상태에서 홈 → 후보 → 내부 조리법을 따라갈 수 있다.
- 카드 이름·선택 이유·상세 레시피·부족 재료가 일치한다.
- 새로고침과 직접 URL 접근에서도 본문이 열리며 JavaScript 실행 전에도 주요 공개 본문과 링크가 있다.
- 예시 재료를 살펴본 것만으로 냉장고 데이터가 바뀌지 않는다.

주요 대상: `HomePage.jsx`, `RecipesPage.jsx`, `RecipeCard.jsx`, `PublicRecipePage.jsx`, 공개 카탈로그 연결 데이터.

### P3. 대표 콘텐츠의 실질적 도움 보강

첫 작업 묶음 제안: **대표 상세 6개 + 재료 허브 2개 + 기존 가이드 2개**. 이는 제작·검토 범위이며 승인 조건이 아니다. 실제 데이터와 검토 가능한 근거를 보고 대상 메뉴를 확정한다.

| 콘텐츠 | 보강할 내용 | 검토 기준 |
| --- | --- | --- |
| 레시피 상세 | 어떤 상황에 고를지, 필수·선택 재료, 근거 있는 대체 조건, 함께 활용할 남은 재료 | 원문과 자체 설명을 구분하고 추천·분량·조리 단계와 모순이 없음 |
| 재료 허브 | 같은 재료로 가능한 3개 안팎의 실제 메뉴 비교 | 추가 핵심 재료·도구·원문 사용량 등 확인 가능한 기준으로 선택을 도움 |
| 냉장고 파먹기 가이드 | 예시 재료 목록부터 메뉴 선택과 구매 목록까지 한 사례를 완결 | 해당하는 실제 레시피에 연결되고 예시와 실제 기록을 구분 |
| 먼저 쓸 재료 활용 가이드 | 남은 재료를 어떤 메뉴로 묶을지 선택 과정 설명 | 날짜만으로 섭취 안전성을 보장하지 않고 보관·안전 관련 내용은 신뢰할 수 있는 자료로 검토 |

예: ‘두부와 달걀이 남았을 때’를 실제 카탈로그 메뉴에 맞춰 구성하고, 각 후보의 추가 재료와 두부 사용량을 비교한다. 구체적인 분량·조리 시간·대체 효과는 자료로 확인한 값만 적는다.

완료 기준:
- 독자가 콘텐츠만 보고 선택 이유와 준비할 것을 설명할 수 있다.
- 원문 출처와 자체 설명의 근거를 표시하며, 검토자는 실제 검토한 날짜를 남긴다.
- 직접 해보지 않은 조리 경험·효과·사진을 실제 경험처럼 표현하지 않는다.
- 문장 수를 늘린 반복 설명 대신 각 항목에 구체적인 판단 정보가 있다.

구현 방식: 기존 JavaScript/JSON 데이터에 recipe ID 기준의 편집 설명을 별도로 연결한다. 원문 카탈로그 갱신 시 자체 설명을 덮어쓰지 않도록 한다. 초기에는 현재 저장소의 편집·검토 흐름을 사용한다.

### P4. 운영 검증과 재심사 준비

작업:
- P0~P3의 결과를 실제 운영 도메인에서 다시 확인한다.
- 데스크톱과 모바일에서 ‘첫 방문 탐색’, ‘재료 보유 추천’, ‘상세 조리법’, ‘가이드 사례’를 점검한다.
- Search Console에서 홈·메뉴·허브·가이드·상세의 대표 URL 실시간 검사와 렌더링을 확인하고 사이트맵을 갱신한다.
- 실제 반영된 변경과 검증 증거를 모아 AdSense 재검토 준비를 완료한다.

완료 기준:
- 공개 대상 URL 접근·본문·메타·내부 링크 검증이 통과한다.
- 빈 재료와 필수 재료 누락 시나리오가 통과한다.
- 대표 방문 흐름에서 로그인 강제, 잘못된 상세 연결, 빈 결과로 인한 막힘이 없다.
- 코드 변경 시 `npm run test:run`, `npm run build`를 실행하고 변경에 해당하는 lint·핵심 E2E를 확인한다.

광고 게재 활성화는 콘텐츠 개선과 별도 출시 점검으로 다룬다. 기존 [AdSense 설정 문서](ADSENSE_SETUP.md)에 따라 게재 위치와 필요한 CSP 출처를 검토하고, 빈 화면·입력·계정·오류 상태에서 광고가 나오지 않는지 확인한다.

색인 완료율·고정 대기일·페이지 수를 승인 보장 조건으로 사용하지 않는다.

| A. 배포 원인 확인과 복구 | 운영 배포 식별, 공개 URL 응답/본문 검사 | 운영 프로젝트 조회 가능 |
| B. 추천 상태와 문구 수정 | 추천 조건 수정, 회귀 테스트 | 로컬에서 바로 진행 가능 |
| C. 홈·메뉴 탐색 개선 | 첫 방문 공개 동선, 프리렌더 검증 | B의 상태 정의 |
| D. 내부 상세 연결 | 검증한 ID 매핑, 부족 재료 표시, 동선 테스트 | 대상 레시피 선정, B |

권장 착수: **A와 B를 함께 시작**하고, C·D·E를 대표 사용 사례 하나로 연결한다. 그 사례가 메뉴 선택부터 조리 준비까지 완결되면 나머지 대표 콘텐츠에 확장한다.

## 6. 이번 계획의 범위

현재 JavaScript·React·정적 공개 콘텐츠·IndexedDB 구조를 활용한다. 대규모 디자인 개편, 새 CMS, AI 추천 확대, 정량 재고 자동 차감은 이번 개선의 선행 작업에 포함하지 않는다.

이 계획에 따라 공개 동선·콘텐츠·추천 수정과 README·CHANGELOG 갱신을 진행했다. 실제 실행한 검사와 미완료 운영 조건은 위 진행 현황 및 검증 기록을 기준으로 판단한다.
