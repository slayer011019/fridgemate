# 가정용 주간 식단 및 영양 정보 구현 계획

작성일: 2026-09-12. 상태: **첫 구현 단위 개발 완료**. 아래 A~E는 전체 로드맵이며 모두 구현됐다는 의미가 아니다. 실제 운영 배포는 실행하지 않았다.

### 이번에 구현한 범위

- `/meal-plan`의 주별 7일 저녁 생성, 1~2인·기피 재료·식사일 설정, 메뉴 교체·고정·건너뛰기·복원.
- `mealPlanCatalog.js`의 16개 기본 메뉴 기반 조합. 출처·선택한 재료·인분/수량 미확인 상태를 보존한다. 재료 구성의 편집 검토이며 영양 전문가 검수나 정량 검증을 의미하지 않는다.
- 날짜별 보유 재료명과 기한 확인, 식품군 구성 안내. 원문 수량과 영양 수치는 만들지 않고, 실제 재고나 기존 재구매 목록을 수정하지 않는다.
- IndexedDB v3 `mealPlans` 저장소, 기존 재료·메뉴 결정 보존, 게스트/계정 분리, 저장 실패·다른 탭 수정 충돌 처리, 현재 기기의 계정 삭제 시 식단 정리. main의 v2(재료·메뉴 결정)와 기능 브랜치의 v2(재료·식단)를 모두 업그레이드한다.
- 반응형 화면, 조건 접기, 키보드 접근, 기능 페이지 noindex. 사용한 기준은 앱의 `composition-v1` 분류이며 2025 KDRI 수치 적용을 주장하지 않는다.

아직 구현하지 않은 범위: 정량 재고 배분·식단 장보기, 날짜 간 메뉴 이동, 조리 완료/실제 사용량 차감, 영양 수치 계산, 개인별 KDRI 비교, 월간 보기, 식단 백업·서버 동기화. 최초 20~30개 카탈로그 목표 중 이번에는 16개를 제공한다.

## 1. 첫 출시의 목표와 범위

성인 1~2인 가구가 집에서 저녁을 먹을 날짜를 고르면, 보유 식재료와 기피 재료를 반영한 7일 저녁 식단을 만들고 메뉴를 교체할 수 있게 한다. 식단에 필요한 장보기 목록과 식품군 구성 안내를 함께 제공한다.

- 입력: 주 시작일, 집에서 먹을 날짜, 인원, 싫어하는 메뉴·재료, 현재 재고.
- 출력: 날짜별 한 끼 구성, 선택 이유, 메뉴 교체·이동·건너뛰기, 부족하거나 수량 확인이 필요한 재료.
- 한 끼는 검수된 한그릇 요리 또는 주식·주요리·반찬의 조합이다. 반찬 하나를 한 끼 전체로 평가하지 않는다.
- 초기 카탈로그는 검수된 레시피·끼니 조합 20~30개를 목표로 한다. 이 수치는 개발 범위 제안이며 확보된 데이터 수가 아니다.
- 먼저 식품군의 포함 여부와 메뉴 반복을 안내한다. 저녁 한 끼로 하루 영양 충족, 단백질 부족·과다, 건강 개선을 판정하지 않는다.
- 식단 선택은 재고를 차감하지 않는다. 실제 소비 반영은 별도의 확인 절차로 구현한다.
- 월간 식단은 장기 목표로 유지한다. 주간 수정 경험을 검증한 후 월간 계획을 세우고 가까운 주를 재고에 맞춰 갱신한다.

[현재 API 안내](https://various.foodsafetykorea.go.kr/nutrient/industry/openApi/info.do), [원재료성식품 표준데이터](https://www.data.go.kr/data/15100065/standard.do), [기존 I2790 설명](https://www.foodsafetykorea.go.kr/api/openApiInfo.do?svc_no=I2790)

최신 연결 후보는 [식품영양성분DB정보](https://www.data.go.kr/data/15127578/openapi.do) 또는 공식 내려받기 자료다. API 활용신청·실제 응답 스키마·호출 한도는 구현 단계에서 확인한다. 기존 FOODSAFETY_API_KEY가 다른 제공 경로에서도 통한다고 가정하지 않는다. 첫 식단 버전은 검수한 소규모 정적 데이터로 동작하게 하고, 이후 서버/관리 스크립트가 필요한 원천 데이터만 가져와 캐시한다. 브라우저에 인증키를 넣거나 사용자의 식단 생성을 외부 API의 실시간 응답에 의존시키지 않는다.

## 4. 구현 단위와 순서

아래 일정은 1인 개발의 순수 작업일 예상이다. 자료 검수 난이도, 외부 API 승인 및 영양 전문가 검토 대기는 별도이며 단계별 통과 조건을 우선한다.

### A. 데이터 계약 및 작은 검수 카탈로그: 3~5일

- 레시피 식별자를 출처와 함께 보존한다. 예: `local:recipe-1`, `mfds:28`. 이름만으로 서로 다른 출처의 요리를 합치지 않는다.
- `mealTemplates`에서 한 끼의 구성 요소와 인분을 명시한다. 밥·반찬을 포함한 영양 값인지, 주요리만의 값인지 기록한다.
- 각 재료 행에 원문, 식별자, 사용량, 단위, 선택 여부, 조리 상태, 근거를 보존한다. 같은 재료가 여러 조리 부분에 나오면 행을 보존한 뒤 호환되는 양을 합산한다.
- 초기에는 검수된 g/kg, ml/L, 동일 규격 개수만 계산한다. 품목별 중량이나 밀도 근거 없는 '모→g', 'ml→g' 변환은 하지 않는다.
- 식품군 태그는 영양성분량과 분리한다. 장식용 대파·소량 양념을 근거로 '채소 충분'을 표시하지 않는다.
- 원문에 없는 레시피 수량·영양 값은 LLM으로 채우지 않는다. 미확인 항목은 `null`과 사유로 남긴다.

완료 기준: 첫 카탈로그의 모든 항목에 출처·인분 검수 상태·식품군·수량 상태가 있고, 일치하지 않는 단위를 조용히 계산하는 경로가 없다.

### B. 주간 식단과 구성 안내, 파생 장보기: 5~8일

- `/meal-plan`에 7일 목록을 추가한다. 모바일에서는 날짜별 카드, 교체·이동 버튼을 우선하고 드래그는 필수로 하지 않는다.
- 식사일·인원·기피 재료를 입력하고 검수된 후보로 초안을 만든다. 조건을 만족하는 후보가 없으면 빈 칸과 이유를 보여준다.
- 메뉴 교체, 날짜 이동, 외식/건너뛰기, 고정, 고정되지 않은 날짜만 다시 추천을 제공한다.
- 추천 우선순위: 기피 재료 제외 → 해당 식사일에 사용할 수 있는 재고 → 임박 재료 활용 → 메뉴 반복 완화 → 식품군 조합 제안. 근거를 짧게 표시한다.
- 식단별 예정 사용량은 선택된 메뉴에서 재계산한다. 같은 재고를 월요일과 수요일에 각각 전량 사용할 수 있는 것으로 처리하지 않는다.
- B 단계에서는 `300g`, `0.5kg`처럼 수치와 단위가 명확한 기존 문자열만 읽기 전용으로 해석한다. 추가 확인값을 받으면 식단 범위 안에 `scope + inventoryId + 원본 quantity + updatedAt`과 함께 저장하고 원본 재고가 바뀌면 무효화한다. 모호한 문자열은 미확인으로 유지한다. 재고 자체의 구조화 필드 저장·차감은 C 단계에서 구현한다.
- 날짜 변경 후 재고·필요 재료·구성 안내를 함께 갱신한다. 실제 재고와 재생성 결과가 달라져도 사용자가 고정한 메뉴를 자동 덮어쓰지 않는다.
- 식단 장보기는 `이번 식단에 필요`라는 별도 목록으로 만든다. 수량이 확인된 항목만 총수요와 가용재고의 차이를 계산한다. 불확실한 재고는 '수량 확인 필요', 필요량만 아는 경우는 '레시피 필요량'으로 표시한다.
- 음식 조리에 필요한 g 수와 상품 판매 포장 수는 구분한다. 구매 완료 체크만으로 재고를 생성하지 않고 실제 구매량을 검토해 재료 등록 흐름으로 연결한다.
- '조리 완료'는 우선 식단 수행 상태만 기록한다. 실제 섭취량이나 재고 차감으로 해석하지 않고 기존 재고 수정 화면을 연결한다.
- IndexedDB에 사용자 범위를 가진 식단을 저장한다. 새로고침·오프라인·로그아웃/계정 전환을 지원하고 현재 장치 저장 상태를 알려준다.

완료 기준: 생성 → 교체 → 장보기 확인 → 저장 → 재접속이 이어지고, 식단 편집으로 실제 재고나 기존 재구매 목록이 바뀌지 않는다.

### C. 확인된 소비량과 재고 연동: 4~6일

- 기존 자유 입력 `quantity`를 보존하면서 확인된 수치·단위·근거를 저장할 선택 필드를 도입한다. 첫 소비량 연동은 로컬 모드에서 검증한다. 계정 모드의 자동 차감은 Prisma·API 검증·직렬화 확장뿐 아니라 아래의 서버 소비 이벤트/조건부 갱신을 갖춘 뒤 출시한다. 오래된 재고의 미확인 수량은 계속 수동 수정한다.
- 조리한 메뉴에서 실제 사용한 재고 항목과 양을 확인하는 화면을 제공한다. 변경된 분량·대체 재료를 입력할 수 있게 한다.
- 수량이 확정된 재고만 부분 차감한다. 한 레시피를 만들었다는 이유로 재료 항목 전체를 `consumed: true`로 처리하지 않는다.
- 식단 수행 기록, 소비 이벤트, 재고 변경을 로컬에서 원자적으로 저장한다. 기존 `clientId`, `updatedAt`, pending sync 규칙을 유지한다.
- 소비 이벤트 ID로 중복 클릭·재시도에 따른 이중 차감을 막는다. 최신 재고와 충돌하면 재확인을 요청한다.
- 취소 시 이후의 사용·구매 변경을 덮어쓰는 과거 스냅샷 복원은 하지 않는다. 이벤트와 최신 재고를 비교해 되돌릴 수 있는 양을 확인한다.
- 식단 계획의 동기화는 여전히 별도다. 기존 재고의 updatedAt 기반 백업은 두 기기의 동시 소비를 합산하는 원장이 아니다. 여러 기기의 소비를 지원하려면 서버의 revision 조건부 갱신, 고유 소비 이벤트의 동기화·중복 제거, 충돌 재확인을 별도로 구현한다.

완료 기준: 현재 장치의 최신 재고를 기준으로 부분 사용, 중복 실행, 저장 실패, 취소에서 음수 재고와 변경 유실이 발생하지 않는다. 다른 기기와의 동시 소비 보존은 서버 이벤트 처리가 도입되는 후속 단계의 완료 기준으로 검증한다.

### D. 수치 영양 정보: 자료 검증 후 별도 1~2주 예상

- 먼저 기준 인분과 구성 요소가 확인된 한 끼의 열량·탄수화물·단백질·지방·나트륨을 표시한다. '선택한 저녁 식단의 예상량'임을 명시한다.
- 공식 식품코드 매핑을 추가할 때 원재료·조리식품·가공식품을 구분한다. 생쌀과 밥, 삼겹살과 앞다리살, 제품별 소스 등을 같은 영양 항목으로 처리하지 않는다.
- 원천 값의 기준량과 실제 사용량을 맞춰 계산한다. `성분량 = 원천 성분량 × 확인된 사용량 / 원천 기준량`은 두 양의 단위와 조리 상태가 같을 때만 적용한다.
- 영양 값은 출처의 1인분 완성 요리 계산 또는 검수된 재료별 계산 중 하나의 경로로 구한다. 두 경로를 더하거나 임의 평균하지 않는다.
- 조리 중 수분 변화·가식부·양념/국물 섭취량·보존계수가 필요한 경우 근거가 없으면 정확한 완성 음식 값으로 제시하지 않는다.
- 결측을 0으로 바꾸지 않는다. 영양소별로 `available / partial / unavailable`과 누락된 구성 요소를 반환한다. 일부 값만 더한 합계에는 일일 충족률이나 양호/부족 등급을 붙이지 않는다.
- 메뉴·인원·구성 요소가 바뀌면 영양량도 재계산하고 출처·계산 기준·버전을 확인할 수 있게 한다.

완료 기준: 공식 자료 또는 수기 계산으로 독립 검수한 사례와 단위 변환·인분 조정·결측 처리 결과가 일치한다. 알려진 값의 최종 표시 반올림과 원천 데이터의 오차를 구분한다.

### E. KDRI 비교와 월간 확장: 주간 사용 검증 후

- 식품군 그림, 권장식사패턴, KDRI 수치 기준을 각각 버전 관리한다. 수정된 기준을 기존 식단에 소급 적용할 때 다시 계산됐음을 표시한다.
- 개인화 목표가 필요해지는 단계에 연령·기준에 필요한 성별·키·체중·활동 수준 등 최소 입력을 설계한다. 사용자가 입력하지 않은 신체정보를 추정하지 않는다.
- 에너지 필요량은 공식 원문의 연령별 식과 활동계수·단위를 검수한 뒤 구현한다. 제3자 사이트의 IOM 계산식을 그대로 복제하지 않는다.
- RNI, AI, UL, AMDR, CDRR 등을 하나의 '권장량' 필드로 합치지 않는다. 예를 들어 AMDR 밖이라는 이유만으로 개인의 단백질 결핍이나 과잉을 판정하지 않는다.
- 식단 계획량과 실제 섭취 기록을 구분한다. 하루 전체를 비교하려면 아침·점심·간식·외식의 기록 범위가 필요하다. 미기록 끼니를 0으로 간주하거나 하루 기준의 1/3을 저녁의 공식 기준으로 고정하지 않는다.
- 초기 대상은 일반 성인으로 한정한다. 아동·임신/수유·질환별 맞춤 목표는 해당 기준과 전문 검토를 갖춘 뒤 별도 확장한다.
- 월간 보기에는 확정한 식사일과 메뉴를 배치하고, 새 장보기·일정 변경은 가까운 주에 우선 반영한다. 재고가 계속 바뀌는 상황에서 한 달의 분량이 모두 확보됐다고 표시하지 않는다.

첫 버전은 순수 함수와 기존 React hook/IndexedDB 패턴을 사용한다. 새 상태관리·최적화·AI 프레임워크는 필요하지 않다. 추천용 별칭과 영양용 식품코드 매핑을 분리하고, LLM은 영양 수치나 재고량의 진실 원천으로 쓰지 않는다.

`src/db/indexedDB.js`를 버전 3으로 올려 같은 범위별 DB에 `mealPlans` 저장소를 추가했다. main의 버전 2에 있던 `menuDecisions`와 기능 브랜치 버전 2의 `mealPlans`를 모두 보존하며, 누락된 저장소만 추가한다. 기존 재고 보존과 `versionchange` 연결 종료, blocked 업그레이드 안내를 구현했다. `shoppingItems`와 C 단계 소비 이벤트 저장소는 별도 버전 상승으로 추가한다. 현재 전역 localStorage 팬트리 저장 패턴을 개인 식단 저장에 복제하지 않는다.

`useAuth().storageScope`를 기준으로 저장·읽기를 격리하고 계정 변경 시 진행 중인 요청을 무효화한다. 현재 게스트 가져오기는 재료만 옮기므로 첫 버전은 식단을 자동 합치지 않는다. 게스트 식단을 유지하고 필요한 경우 명시적인 복사 동작을 후속 추가한다. 계정 삭제·로컬 데이터 정리 시 새 저장소의 처리도 포함한다.

`src/components/AppRoutes.jsx`, `src/App.jsx`, `src/AppServer.jsx`에 페이지를 등록한다. 식단 경로는 개인 기능 화면으로 취급한다. 라우팅·검색 메타·배포 라우트 규칙에 noindex 앱 셸 경계를 추가하고 공개 레시피 페이지의 프리렌더를 유지한다.

후속 서버 식단 저장은 사용자 소유 `MealPlan`·`ShoppingItem`과 고유 소비 이벤트, revision·삭제 tombstone을 설계하고 `server/src/db/tenantScope.js`의 범위 지정과 RLS를 적용한다. 현재 재료 동기화에 식단을 끼워 넣는 방식은 사용하지 않는다.

## 6. 데이터 계약의 최소 항목

- **MealPlan:** `id`, `schemaVersion`, `scope`, `weekStart`, `preferences`, `slots`, `revision`, `createdAt`, `updatedAt`. 날짜는 지역 달력 기준 `YYYY-MM-DD`로 저장한다.
- **MealSlot:** `id`, `date`, `mealType: dinner`, `status: planned/cooked/skipped`, `locked`, `servings`, 구성 레시피 키·버전·분량. 이미 조리한 슬롯은 재생성으로 교체하지 않는다.
- **RecipeIngredientLine:** 출처 행 ID, 원문명, 추천용 키, 영양용 식품코드(추후), 양·단위·조리 상태·검수 상태. 중복 재료 행을 임의 삭제하지 않는다.
- **Inventory allocation:** 재고 항목 ID, 슬롯 ID, 예정량, 단위, 수량 확인 상태. 식단과 현재 재고에서 파생하며 오래된 배분을 그대로 저장해 신뢰하지 않는다.
- **Verified inventory quantity(C 단계):** 기존 표시 문자열과 함께 확인된 수치·단위·변환 근거·확인 시점·revision. 영수증의 구매 포장 수와 가식부 g을 구분한다.
- **Shopping item:** `origin: meal-plan`, 연결된 슬롯들, 재료 식별자, 필요량, 부족량 또는 미확인 사유, 단위, 체크 상태. 구매 및 재고 생성은 별도 동작이다.
- **Consumption event(C 단계):** 고유 이벤트 ID, 슬롯 ID, 사용한 재고 항목별 실제 양, 실행 시점과 변경 전 revision. 원자적 저장과 재시도 방지에 사용한다.
- **Nutrition source(D 단계):** `source`, `sourceFoodCode`, `sourceVersion`, `basisAmount`, `basisUnit`, `preparationState`, `nutrients`, `retrievedAt`, `reviewedAt`. 영양소마다 값과 단위를 보존한다.
- **Reference manifest(E 단계):** KDRI 판본, 정오표 적용일, 표·페이지, 지표 종류, 대상 조건, 단위, 식사패턴 자료 버전, 검수자/일자.

개인 식단과 취향은 사용자 범위 밖으로 노출하지 않는다. 서버 저장을 도입하면 계정별 조회·수정·삭제, 내보내기·탈퇴 삭제, 데이터 보유 정책에 함께 포함한다. 식단/취향 원문을 분석 이벤트로 전송하지 않는다.

## 7. 검증과 출시 조건

### 기능 및 회귀 검증

1. 기피 재료, 고정 메뉴, 건너뛴 날짜는 재생성으로 위반되지 않는다. 후보가 없으면 이유를 표시한다.
2. 사용자별 식단이 섞이지 않고 늦게 끝난 저장이 다른 계정의 화면/저장을 덮어쓰지 않는다.
3. 기존 IndexedDB 자료가 있는 장치의 업그레이드, 새로고침, 오프라인 저장, 저장 실패를 확인한다.
4. 동일 재고 300g을 두 끼가 각각 200g씩 요구하는 검증용 사례에서는 부족 100g을 표시한다. 재고를 두 번 전액 인정하지 않는다.
5. '두부 1모'에 중량 근거가 없으면 g 기준 부족량을 산출하지 않는다. 선택한 식사일 이전에 기한이 지난 재고는 그 날짜의 가용량에 포함하지 않는다.
6. 메뉴 교체·이동·인원 변경 후 필요량과 장보기 연결이 갱신된다. 기존 소비 완료 재구매 목록과 체크 상태를 불필요하게 덮어쓰지 않는다.
7. 조리 완료 반복 클릭, 부분 소비, 중간 저장 실패, 취소를 검증한다. 실제 소비 연동 출시 전에는 어떤 경로에서도 자동 차감되지 않는다.
8. g/kg, mg/g, 인분 배수, 생것/조리된 것 구분, 결측/0 차이, 반복 재료량 합산을 독립 계산 사례로 확인한다.
9. 식단 일부만 기록됐거나 영양 값이 누락된 경우 '하루 영양 충족', '단백질 부족' 등을 표시하지 않는다.
10. 모바일 버튼·키보드 조작으로 교체/이동 가능, 공개 페이지 SEO 유지, 새 기능 경로 noindex를 확인한다.

구현 PR마다 `npm run lint`, `npm run test:run`, `npm run build`를 실행한다. E2E는 식단 생성·교체·저장·계정 전환을 추가했으며 장보기와 C 단계 소비 재시도/취소는 해당 구현 때 확장한다. 실제 검증 결과는 아래 첫 구현 기록과 구분해 남긴다.

### 실제 사용 검증

초기에는 5가구 안팎의 자발적 참여자에게 2주간 사용하게 하는 것을 제안한다. 참여 규모와 기간은 제품 검증용 제안이며 사용자 모집 실적이 아니다.

- 만들어진 식단 중 확정한 메뉴, 교체·건너뛴 메뉴와 이유, 조리했다고 확인한 메뉴를 구분한다.
- 메뉴를 정하는 데 걸린 시간, 수정의 편의성, 장보기 누락·과잉 사례를 관찰한다.
- 소비 버튼만으로 실제 섭취나 폐기 감소·식비 절감을 입증하지 않는다.
- 사용자마다 다음 주 식단을 다시 만들 의사가 생겼는지 확인한 뒤 월간 보기·유료화·정량 영양 중 다음 우선순위를 정한다.

## 8. 첫 구현 PR의 범위

첫 구현은 A 단계의 데이터 계약과 기본 메뉴 기반 샘플, B 단계의 최소 동작인 '한 주 생성 → 메뉴 하나 교체 → 범위별 로컬 저장'을 제공한다. 수량이 미확인된 경우의 안내와 식품군 표시를 포함한다. 이후 식단 유래 장보기, 사용량 확인, 정량 영양을 각각 검증 가능한 변경으로 나눈다.

후속 구현 전 남은 확인은 카탈로그의 실제 분량 근거, 영양 API 응답과 이용 조건, 식사패턴의 확정 판본이다. IndexedDB 업그레이드·계정 정리 경로는 첫 구현에서 테스트했다. 현재는 영양 API 없이 소규모 메뉴의 주간 계획 UI와 로컬 저장이 동작한다.

### 첫 구현 검증 기록

- 식단 도메인·식품군·저장소·훅·화면·DB·계정 정리 집중 테스트 7개 파일, 83개 검사 통과.
- 전체 브라우저 E2E 19개 통과: 신규 식단 3개와 기존 CRUD·OCR·로그인·동기화 흐름을 함께 확인했다.
- 프로덕션 빌드와 공개 113개 경로·사이트맵·noindex 앱 셸 검증 통과. 운영 배포는 하지 않았다.
- 현재 프로젝트 ESLint 통과. 중첩된 `.worktrees/`와 브라우저 테스트 출력물은 검사 대상에서 제외했다.
- 전체 단위 테스트에서 기존 추천의 주재료·양념 중복 분류 관련 17건 실패를 발견했다. 해당 파일은 착수 전부터 미커밋 변경이 있던 별도 영역이라 이 작업에서는 수정하지 않았다. 전체 테스트가 통과한 것으로 보고하지 않는다.

### 푸시 대상 분리 검증

원래 작업 트리의 SEO·추천·편집 콘텐츠 변경을 제외하고 식단 관련 파일과 문서 변경만 별도 검증 폴더에 구성했다. 이 푸시 대상에서는 전체 단위 테스트 91개 파일·482개 검사, 브라우저 E2E 19개, ESLint, 빌드 및 113개 공개 경로 SEO 검증이 모두 통과했다. 위 17건의 실패가 발생한 별도 미커밋 변경은 커밋에 포함하지 않았다.

브랜치는 `8efa882`를 기준으로 한 `codex/weekly-meal-plan`이다. 원격 `main`의 이후 변경은 덮어쓰지 않았으며, 최신 `main`과의 통합·운영 배포는 별도 작업이다.
