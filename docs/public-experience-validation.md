실시간 404는 일반 HTTP 검사와 일치한다. robots 차단으로 판단할 근거는 없으며, 새 공개 콘텐츠 배포가 먼저 필요하다. 레시피 보고서의 선택 항목 경고를 채우기 위해 실제 평가·영상·조리 시간을 만들어 넣지 않는다. 재배포 후 본문과 분량이 일치하는지, 위 오류 대상 2개가 Google 실시간 검사에서 정상인지 확인해야 한다.

로컬 완성 빌드는 인앱 브라우저에서도 홈 → 내부 대표 상세로 이동해 준비 목록·전체 조리 단계·출처 링크를 확인했다. 홈의 대표 이미지가 실제 외부 소스에서 표시되는 것도 확인했다. 이는 운영 도메인 배포 검증을 대체하지 않는다.

## 서버 배포 선행 조건

Cloudflare 인증이 없어 현재 배포 Worker의 버전/커밋은 조회하지 못했다. 공개 health의 HTTP 200이나 보호 경로의 401은 새 소스 전체가 이미 배포됐다는 증거가 아니다.

운영 DB는 READ ONLY 트랜잭션으로 migration 및 schema 메타데이터만 조회했다. 사용자 재료·계정 데이터, DDL/DML은 조회·실행하지 않았다.

- 로컬 migration 26개 중 운영 완료 19개, 미적용 7개. 실패 상태 또는 알 수 없는 운영 migration은 없었다.
- 미적용: `20260830180000`, `181000`, `182000` 이벤트 인덱스, `190000`, `191000`, `192000` 삭제 레코드 제약/nullable 전환, `200000` advisor hardening.
- 기존에 문서화된 체크섬 차이 2개 외 `20260527120000_add_recommendation_events` 차이가 발견됐다. 기존 `8efa882`와 최신 `ca7b6d2` 모두 운영 기록과 달라 이번 공개 복구에서 생긴 차이는 아니다. 기존 이력 확인 전 checksum을 덮어쓰지 않는다.
- 2026-09-06 14:03:27 KST 운영 schema에서 `Ingredient.name/category/storageType/quantity/consumed/createdAt`는 모두 NOT NULL이고 `Ingredient_active_payload_required` 제약은 없었다.
- 현재 서버의 `deleteIngredientById`는 `createScrubbedIngredientTombstone`으로 위 필드를 null 처리한다. 따라서 현재 소스를 이 DB에 바로 배포하면 재료 삭제·삭제 동기화가 실패한다.

기존 배포 문서의 순서대로 `20260830190000 → 191000 → 192000`을 검토·적용하고 서버를 배포해야 한다. 나머지 미적용 migration과 기존 checksum 차이도 운영 기준으로 검토해야 하므로 전체 `prisma migrate deploy`를 무조건 실행하지 않는다. 관련 내용은 [배포 문서](CLOUDFLARE_DEPLOYMENT.md)와 README의 tombstone 전환 순서를 참조한다.

이번 작업에서는 DB migration·이력 수정·Worker 배포를 실행하지 않았다. 프런트엔드 복구와 서버 출시 완료는 별도로 확인한다.

원래 체크아웃에는 사용자의 기존 수정과 초기 중간 작업이 남아 있다. 이를 정리하는 `git restore`가 자동 승인 검토에서 미커밋 작업 손실 위험으로 거부되어 그대로 보존했다. 배포·검증 기준은 위 별도 작업 트리다.
